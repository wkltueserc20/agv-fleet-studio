朝 WCS／RCS／ECS 分工發展

參考 KUKA.AMR Fleet 2.13 手冊第 15–16、501–502 頁；以下是本專案的分階段設計，不代表已達 KUKA 功能規模。

名稱對照：原「中央」現在統一稱「外部介接入口」，服務名稱為 integration-service。目前負責接收、轉交與查詢，不代表已具備完整 API Gateway 的認證與限流功能。既有網址 :8210、API 路徑及相容用的 role: central 保留；歷史紀錄不回寫改名。

外部人員 → 介接服務 API → WCS；WCS 分別協調 RCS 與 ECS。RCS 對 AGV 派發動作，ECS 對外部設備／機台 PLC 讀寫信號；結果往上回報。

WCS（Workflow Control）管流程：保存整張作業 job，決定先後順序、等待條件及異常。RCS 管車：選車、鎖定車輛、路徑與交管。ECS 管設備：機台就緒、允許交接、完成與復位。車上馬達、煞車與安全 PLC 仍屬 AGV。

  1. 第一階段：WCS 作業流程＋ECS 模擬設備握手；同一張作業鎖定同一台車，沿用 RCS MOVE，不以到站冒充取放料完成。
  2. 第二階段：補足車端取放料動作、實際感測與設備握手，整張作業取消已加入；本機設備逾時、人工對帳、故障復歸與人工接續已實作；後續補真設備感測與斷線驗收。
  3. 第三階段：依 API_STANDARD.md 完成版本化 OpenAPI、外部與設備權限、可設定位址與部署。先分責任，再決定是否拆成多個專案或電腦。

第一階段已實作（模擬） 使用獨立 WCS :8215、ECS :8216 程序。整張作業與設備交接分別存在 wcs.json／ecs.json；RCS 保存作業用車鎖定。新整張搬運作業走介接服務 /api/jobs；/api/tasks 保留 RCS 單項 MOVE 及舊 TRANSPORT 相容性。舊任務不會被轉寫或重跑。

目前八個交接設備為 A、B、C、WIP、CUT、CNC、OVEN、PACK；充電、待命及避讓點使用 MOVE，不作為取放料機台。模擬設備提供有料、可收料、故障與自動完成開關。流程等待真正的模擬握手結果；尚未連接實際 PLC，也沒有真實取放感測。重啟時，非取消中的已鎖車未完成作業與未完成設備交接會停在待確認；取消中的作業繼續查證。保留資源，不自動重做取放料；已派出的移動仍可能完成。已新增整張作業取消：先顯示取消中，協調 RCS／ECS 停止與確認；無載貨、位置及道路都確認後才已取消。載貨或不確定結果轉待人工確認並保留資源。取消確認預設 60 秒逾時轉人工處理；人工對帳與模擬復歸畫面已實作；設備等待逾時已有本機版本；真車驗證仍列為下一階段。

電池與充電電量、是否充電、電池異常；安排充電並判斷可否派車。固定模擬值

目前電量固定 85%。CHG1／CHG2 是可導航的充電停靠點；尚無耗電、自動充電或充電樁通訊。

載貨狀態空載／有貨、貨物或載具編號；避免派錯搬運任務。待補齊

WCS 已保存作業的模擬載貨旗標，人工接續也會記錄載貨確認；AGV 尚無獨立載貨感測回報、貨物／載具識別，不能把人工確認當真車感測。

安全狀態急停、安全雷射觸發、保護停止；停止相關派單並顯示原因。待補齊

目前的「暫停」是軟體模擬控制，不是安全急停，也沒有接入安全裝置。

異常資訊異常代碼、說明、發生與解除時間；判斷等待、重試或人工處理。部分具備

已有回報連線錯誤、儲存錯誤與待確認說明；尚無車輛故障碼、異常等級及解除流程。通訊錯誤不等於車輛故障。

② 任務回報：描述每張任務怎麼執行

與固定車況更新分開，任務結束後也不應停止車況監測。

資料類別AGV 應提供的內容／RCS 用途目前狀態與尚缺內容
任務狀態任務編號、已接受／執行中／完成／取消／失敗；更新生命週期。部分具備

已有接單確認、執行中、完成與取消。尚須補齊車端任務失敗回報、失敗原因與後續處理；不能只靠 RCS 的「待確認」取代失敗結果。

任務進度目前步驟、進度、等待原因；顯示取貨、行駛、放貨或等待。已具備（模擬）

已有 task_id、progress、phase、序號及等待原因；真實取放貨確認仍需車端／PLC 回報。

指令確認指令編號、接受／拒絕、原因；確認派單、暫停及取消是否被接受。部分具備

已有派單 accepted、重送去重、HTTP 錯誤與取消回報；尚無統一的指令編號、結構化拒絕代碼與跨重啟確認協定。

路徑執行核准路徑編號、到達點位、目前路段；確認道路是否可釋放。已具備（模擬）

已有 route_token、route_path、點位與路段。RCS 以新車況確認到站後釋放預約；真車到站、定位與安全條件仍需另接入。

③ 待執行事項與建議順序

下列只保留尚未完成的功能；已完成的取消、設備逾時、人工結案與接續請見上方總表。

  1. 優先 1

    外部通知、接手與升級紀錄

    工作台待確認清單、等待時間、資源提示及可設定黃／紅提醒已完成；後續加入通知指定人員、已讀／接手及值班升級。

    完成判準：通知對象與升級規則可設定，保留送出、已讀與處理紀錄；通知不代替現場確認，也不自動釋放資源。
  2. 優先 1

    獨立車況上報／心跳與通訊逾時

    建議目標：不論待命、暫停或執行中，每秒固定提供車況；與任務進度回報分開。加入最後有效回報時間、可設定逾時門檻，逾時停止派新任務。

    完成判準：沒有任務時仍可看到新車況；斷線後正確標示逾時，重新連線也有明確恢復條件。現在仍由 RCS 定時 GET 查詢，不是這個主動心跳。
  3. 優先 1

    明確定義「可派車」條件

    補齊自動／手動模式、故障、安全、載貨與電量欄位；統一狀態值、單位及缺值的處理方式。

    完成判準：手動、故障、保護停止或資料不可信的車，不會收到不適合的新任務。
  4. 優先 1

    任務失敗與指令拒絕原因

    建立結構化的異常／拒絕代碼，區分「未接受」「已接受但失敗」「結果未知」，並定義重試或人工處理方式。

    完成判準：RCS 能顯示實際失敗原因；結果未知時不會重複派出可能已被接受的任務。
  5. 優先 1

    車端重啟識別與重新同步

    加入啟動編號、車況序號及介面版本；重新連線時核對任務、位置與預約，辨識重啟前的舊資料。

    完成判準：重啟後不把舊回報當新狀態，不自動釋放位置尚未確認的道路。
  6. 後續

    充電、載貨與真車／PLC 接口

    補上電量模型、充電條件與充電樁確認，再接取放貨感測、安全狀態與實際車端。每一項都要有對應的異常與恢復測試。

  7. 後續

    交管效率與復原流程

    本機取消、結案復歸與設備步驟接續已具備。仍待補逐段釋放、任務優先順序、忙碌車互等處理、半路中斷接續，以及真車的取消／重啟復原驗證；目前仍採保守的整趟路徑預約。

④ 使用與開發注意事項

查詢與主動回報是兩個方向

目前 RCS 約每 0.5 秒查詢車端 GET /api/state；API 紀錄每 2 秒取樣。任務推進時，AGV 以 POST /api/events 主動回報。獨立車況上報／心跳仍待新增。兩種傳輸方式都需要明確的資料內容。

「有回應」不等於「可派車」

目前 online 主要表示模擬服務可連線，不代表真車已就緒。能否派車仍須核對模式、安全、故障、電量、載貨、任務及資料時效。

取消、離線或重啟，不能直接視為道路已清空

目前會保留未確認的道路預約；「模擬復歸」會直接設定模擬位置，不能照搬成真車的復原操作。

安全停止由車端與安全控制系統執行

RCS 可停止派單與顯示原因，但不能把安全急停、避障或保護停止只交給網路與 RCS 處理。目前尚未連接真實 AGV、PLC、ROS 或海康 RCS。
